## Contexto

[Placeholder] O cliente desenvolve um software de análise usado todos os dias por pesquisadores em laboratórios.
O produto cresceu ao longo de mais de 10 anos, com vários times adicionando funcionalidades sem uma base de UI compartilhada.

## Problema

[Placeholder] Cada tela parecia um pouco diferente. Os devs recriavam os mesmos componentes,
novas funcionalidades levavam semanas de design e QA, e os usuários tinham dificuldade para aprender a ferramenta.

- 12 estilos de botão diferentes e 7 variações de tabela
- Nenhuma documentação ou token compartilhado entre design e código
- Problemas de acessibilidade em tabelas de dados densas

## Meu papel

[Placeholder] Liderei o design system de ponta a ponta: auditoria, arquitetura de tokens, biblioteca de componentes,
documentação e adoção com dois squads de engenharia.

## Processo

[Placeholder] **Auditoria →** inventariei mais de 300 telas e agrupei os padrões.
**Fundamentos →** defini tokens de cor, tipografia, espaçamento e densidade para telas com muitos dados.
**Componentes →** construí 40 componentes no Figma espelhados 1:1 no Storybook.
**Adoção →** fiz plantões semanais e pareei com devs nas primeiras migrações.

## Decisões-chave

1. **Modos de densidade como tokens.** Pesquisadores precisam de tabelas compactas; usuários novos precisam de respiro.
   Um único token de `density` alterna os dois sem novos componentes.
2. **Tabelas primeiro.** A tabela de dados é 60% do produto, então foi o primeiro componente lançado.
3. **Documentação junto do código.** O Storybook virou a fonte da verdade; o Figma o espelha.

## Resultado

[Placeholder — substituir por números reais]

- **−40%** no tempo entre design e desenvolvimento de novas funcionalidades
- **90%** das telas migradas para o sistema em 6 meses
- Contraste **AA** nos fluxos principais

## Aprendizados

[Placeholder] Um design system é um produto: precisa de usuários (os devs), roadmap e
métricas de adoção — não só de uma biblioteca de componentes.
